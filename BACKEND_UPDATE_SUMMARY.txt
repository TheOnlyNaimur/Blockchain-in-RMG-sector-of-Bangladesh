WHAT CHANGED
================================================================================

BEFORE:
  - Accepted: { txHash, userAddress, name, license, contact }
  - Logic: Wait for transaction that was already broadcast by MetaMask
  - Security: Relied on frontend only, no backend verification

AFTER:
  - Accepts: { data, signature, userAddress }
  - Logic: Verify signature → Hash data → Call contract → Store record
  - Security: End-to-end verification with cryptographic proof

================================================================================
5-STEP BACKEND FLOW (Each Registration)
================================================================================

1. SIGNATURE VERIFICATION
   - Reconstruct the original message from received data
   - Use ethers.verifyMessage(message, signature) to recover signer's address
   - Compare recovered address with claimed userAddress
   - If mismatch → Reject request with 401 error

2. DATA HASHING
   - Hash the data using ethers.keccak256()
   - This hash proves "this exact data was submitted at this time"
   - Used as reference on-chain

3. CONTRACT CALL
   - Get a contract instance signed with BACKEND_PRIVATE_KEY
   - Call contract.registerBuyer(userAddress, dataHash) or
          contract.registerSeller(userAddress, dataHash, tinid, number)
   - Transaction is broadcast by backend to blockchain

4. RECEIPT VERIFICATION
   - Wait for transaction confirmation (1 confirmation, 60 second timeout)
   - Check receipt.status === 1 (success) or 0 (failed)
   - If failed → Error response, database unchanged

5. DATABASE STORAGE
   - Only if Step 4 succeeded
   - Store: userAddress, data, signature, dataHash, txHash, blockNumber, timestamp
   - This creates full audit trail

================================================================================
ENVIRONMENT VARIABLES REQUIRED
================================================================================

In backend/.env, add:

BACKEND_PRIVATE_KEY=0x....(private key of account that will call contracts)

This account must have:
- ETH balance to pay for gas
- No special role restrictions (can call any function)

Example (for testing with Anvil Account #0):
BACKEND_PRIVATE_KEY=0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80

Note: Different from CERTIFIER_ACCOUNT_PRIVATE_KEY
      BACKEND_PRIVATE_KEY = Used for buyer/seller registration
      CERTIFIER_PRIVATE_KEY = Used only for seller approval

================================================================================
ERROR RESPONSES
================================================================================

400 Bad Request:
  - Missing required fields (data, signature, userAddress)
  - Invalid data structure
  - Example: { "success": false, "error": "name is required in data" }

401 Unauthorized:
  - Invalid signature format
  - Signature doesn't match user address
  - Example: { "success": false, "error": "Signature does not match user address" }

500 Server Error:
  - BACKEND_PRIVATE_KEY not configured
  - Transaction reverted on-chain
  - Example: { "success": false, "error": "Transaction failed or reverted" }

================================================================================
SUCCESS RESPONSE
================================================================================

200 OK:
{
  "success": true,
  "txHash": "0x...(transaction hash on blockchain)",
  "blockNumber": 42,
  "message": "Buyer registered successfully."
}

The txHash can be used to:
  - Look up transaction details on block explorer
  - Verify on-chain execution
  - Prove transaction occurred at blockNumber

================================================================================
SECURITY FEATURES
================================================================================

✓ No Private Key Input: Frontend never sends private key
✓ Cryptographic Proof: Signature proves user authorized this
✓ Tamper Detection: Hash proves data wasn't modified
✓ Backend Verification: Server verifies before contract interaction
✓ On-Chain Proof: Transaction hash provides immutable record
✓ Database Audit: Full trail of user, signature, data, timestamp

================================================================================
DATABASE STORAGE
================================================================================

When registration succeeds, database stores:

{
  "eventType": "BUYER_REGISTERED",
  "buyerAddress": "0x...",
  "name": "John Doe",
  "license": "LIC-123456",
  "contact": "+1234567890",
  "signature": "0x...(user's digital signature)",
  "dataHash": "0x...(keccak256 hash of data)",
  "txHash": "0x...(blockchain transaction hash)",
  "blockNumber": 42,
  "timestamp": 1711234567890
}

This allows later verification:
  - Prove user signed (using signature)
  - Prove data integrity (using dataHash)
  - Prove on-chain execution (using txHash, blockNumber)

================================================================================
MIGRATION FROM OLD SYSTEM
================================================================================

Old Frontend: Send { privateKey, ...data }
Old Backend: Use that private key to call contract
Old Security: Low (private key exposed over network)

New Frontend: Send { data, signature, userAddress }
New Backend: Verify signature, then call contract with backend key
New Security: High (private key never leaves user's device)

To migrate:
1. Update frontend to use MetaMask signMessage
2. Update frontend to send { data, signature, userAddress }
3. Add BACKEND_PRIVATE_KEY to backend/.env
